# TRAE CN 3.4.4 编码能力判分（2026-10-22 / 10-23）

- 被测：TRAE CN 3.4.4，Agent 窗口，模型 `deepseek-v4-flash`，手动审批，本地执行
- 环境：Windows Server 2022，2560×1288，CDP 驱动；每轮一个独立 fixture 副本（git baseline + 快照）
- 方法：`code-eval/`，5 个任务 × 3 次 = **15 次尝试**（另有 L1–L3 的第一批 9 次，结论一致）
- 判分：隐藏验收（每个任务 8–9 条）始终在 agent 上下文之外，判分只看行为，不看 diff 长相

## 结果

| 任务 | 档 | 通过 | 耗时 | 授权 | 改动 |
|---|---|---|---|---|---|
| `L1-split-bill` | L1 单文件修 bug | 3/3 | 16–18s | 2 | +7…+9 / −2…−3 |
| `L2-todo-due` | L2 多文件加功能 | 3/3 | 22–38s | 2 | +44…+56 / −2…−4 |
| `L3-sales-pipeline` | L3 跨模块三处缺陷 | 3/3 | 34–39s | 3 | +15…+22 / −7…−11 |

| `L4b-ledger-ambiguous` | L4 同一仓库，只给症状 | 3/3 | 48–60s | 4 | +23…+26 / −10…−13 |

**15/15 通过。** 加上第一批 L1–L3 的 9 次，共 24 次尝试没有一个任务被判失败。

## 结论

**1. 五档任务都拦不住它，难度还不够。** 单文件、多文件、跨模块、六文件排错、只给症状不给规则，
全部 3/3。这套题现在能回答「它会不会在这些任务上翻车」，答案是不会；还不能回答「它和别的工具谁强」。

**2. 含糊需求没有明显更差。** `L4b` 只描述症状（「3 月总额少了、月底几笔跑到 4 月、周末美元折算不对、
e4 算了两遍」），不给任何规则，它照样把时区归月、交易日回溯、`amend` 覆盖三条都推了出来。
过拟合不了的一点：这是同一个 fixture，规则在别处（README / 数据）能对上，不一定等于真实业务里也能。

**3. 授权次数随文件数上升，这是目前唯一稳定的成本信号。** L1/L2 每次 2 次授权（改文件 + 跑测试），
L3 3 次，L4/L4b 4–5 次。耗时从 17s 涨到 53s，增长主要来自多文件编辑和多次跑测试。

**4. 偶发停顿值得产品方排查。** 含糊组的第一批里出现过 2 次「跑完复现命令就停住、不改代码」，
同一提示下另外 3 次正常完成。停顿会直接表现为 0 分，但不稳定复现，先记为观察项，不算能力结论。

## 判分口径的一次误判（必须记）

第一批 L4b 判出 0/3 之后查了 trace：其中一次在提交后 2 秒就被判分——侧栏「任务完成」计数
在上一轮任务收尾时被误触发，判分跑在了 agent 动手之前。去掉这个信号、改用「界面 idle 窗口」后，
同一批 3 次全部改完并通过。

结论：**判分器本身要先被证伪。** 现在 `tools/selftest.py` 用 15 个假 agent 用例守住口径
（正确解 / 原样不动 / 只讨好可见用例 / 漏校验 / 改 tests / 只修一半），真机上再遇到「低分」先看
trace 里有没有提前判分，再谈工具能力。

## 下一步（按优先级）

1. **长任务**：5–10 步、要自己拆解、中途要跑测试并回改；现在的任务都一次成型
2. **大仓库**：200+ 文件、同名字段、无关模块，考定位而不是考读三个小文件
3. **硬约束**：性能/内存上限、并发、向后兼容旧数据；这类验收更难糊弄
4. **多工具对照**：同一任务换工具/模型跑，才轮得到「值不值得买」

## 边界

- 一个工具、一个模型、五个小任务；每任务 3 次只够说「稳定」，不够说「编程能力总分」
- fixture 都是百行级仓库，`L4b` 的规则虽然没写进 prompt，但能在 README 和数据里对上
- 判分只看行为，绕过验收（改 `conftest.py`、`sitecustomize.py`）靠 `forbidden` 拦，拦不全
- 耗时按 trace 的「提交 → 界面最后一次变化」计，不含驱动器等待窗口（L4b 为 150 秒）
- 驱动器会代点「本次会话允许」；真实使用中这一步是人工摩擦，授权次数已单独记录
