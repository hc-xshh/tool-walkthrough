# TRAE CN 3.4.4 编码能力判分（2026-10-22 / 10-23）

- 被测：TRAE CN 3.4.4，Agent 窗口，模型 `deepseek-v4-flash`，手动审批，本地执行
- 环境：Windows Server 2022，2560×1288，CDP 驱动；每轮一个独立 fixture 副本（git baseline + 快照）
- 方法：`code-eval/`，6 个任务 × 3 次 = **18 次尝试**（另有第一批 L1–L3 的 9 次，结论一致）
- 判分：隐藏验收（每个任务 8–11 条）始终在 agent 上下文之外，判分只看行为，不看 diff 长相

**18/18 通过。** 加上第一批 L1–L3 的 9 次，共 27 次尝试没有一个任务被判失败。

## 结论

**1. 五档任务都拦不住它。** 单文件、多文件、跨模块、六文件排错、只给症状、五条规则的长任务，
全部 3/3。L5 是代价最高的一条（74–93 秒、约 100 行改动），但结果一样。

**2. 成本随复杂度上升，这是目前唯一稳定的区分信号。** 授权 2 → 3 → 4–5 次，耗时 17s → 53s → 88s，
改动行数 +7 → +30 → +100。对「推给团队」这个决策，这个维度比通过率更有信息量。

**3. 剩下没被验证的轴只有两个**：仓库规模（现在是百行级，真实项目千行起）和多轮需求变更
（现在的任务一次交代完，真实工作是「先这样、再改一版」）。这两条不试，「它行不行」就只能停在
「在我出的题上行」。

## 判分器的两次误判（这是本轮最有价值的产出）

**第一次：提前判分。** L4b 第一批判出 0/3。查 trace 发现有一次在提交后 **2 秒**就判分——
侧栏「任务完成」的计数被上一轮任务收尾误触发。去掉这个信号、改成界面 idle 窗口后，同一批 3/3。

**第二次：验收比任务书更严。** L5 第一批判出 1/3，两次都只挂在 `test_replay_is_idempotent`。
查失败信息：状态确实幂等了，只是重放时把 `deleted` 又加了 1；而任务书只要求「重放 `applied` 为 0」，
是我的断言多写了 `skipped/deleted` 的计数口径。按任务书改回后，同一批 3/3。

两条规则现在是硬约束：

- 判分器自己要先被证伪：低分先看 trace 里有没有提前判分、验收有没有超出任务书；
- **每条隐藏验收必须能对到任务书的一句话**，对不上的，删掉，或者补进任务书。

`tools/selftest.py` 守住第一类（19 个假 agent 用例：正确解 / 原样不动 / 只讨好可见用例 /
漏校验 / 改 tests / 只修一半 / 不看墓碑），第二类只能靠人对着任务书逐条核。

## 下一步（按优先级）

1. **大仓库**：200+ 文件、同名函数、无关模块，考定位；这是唯一没试过的规模轴
2. **多轮变更**：先给一版需求，跑完再追加「把 A 改成 B」，看它会不会破坏上一轮
3. **多工具对照**：同一任务换工具/模型跑，才轮得到「值不值得买」

## 边界

- 一个工具、一个模型、六个百行级任务；每任务 3 次只够说「稳定」，不够说「编程能力总分」
- `L4b` 的规则虽然没写进 prompt，但能在 README 和数据里对上；真实业务里的含糊比这更狠
- 判分只看行为，绕过验收（改 `conftest.py`、`sitecustomize.py`）靠 `forbidden` 拦，拦不全
- 耗时取 trace 与文件 mtime 的较大值，不含驱动器等待窗口
- 驱动器会代点「本次会话允许」；真实使用中这一步是人工摩擦，授权次数已单独记录
