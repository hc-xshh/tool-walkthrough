# TRAE CN 3.4.4 编码能力判分（2026-10-22 / 10-23）

- 被测：TRAE CN 3.4.4，Agent 窗口，模型 `deepseek-v4-flash`，手动审批，本地执行
- 环境：Windows Server 2022，2560×1288，CDP 驱动；每轮一个独立 fixture 副本（git baseline + 快照）
- 方法：`code-eval/`，7 个任务 × 3 次 = **21 次尝试**（另有第一批 L1–L3 的 9 次，结论一致）
- 判分：隐藏验收（每个任务 8–11 条）始终在 agent 上下文之外，判分只看行为，不看 diff 长相

## 结论

**1. 七档任务都拦不住它。** 单文件、多文件、跨模块、六文件排错、只给症状、五条规则的长任务、
两轮需求变更，全部 3/3。

**2. 多轮变更没有变难，只是变贵。** L6 的第二轮是把物理删除改成软删除，牵扯 `sync.py` 的
合并逻辑、`cli.py` 的新子命令和旧墓碑迁移；三次都做对了，包括「第一轮的规则不能改坏」。
代价是单次从 85 秒涨到 4 分钟上下——第二轮要重读代码、重跑测试。

**3. 成本是目前唯一稳定的区分信号。** 授权 2 → 3 → 4–7 次，耗时 17s → 85s → 255s，
改动行数 +7 → +30 → +100。

**4. 剩下的轴：规模。** 现在最大的仓库也就 6 个文件、200 行。真实的千行仓库、同名函数、
无关模块，考的是定位而不是读代码——这一条还没试，「它行不行」只能停在「在我出的题上行」。

## 判分器自己错了三次（这是本轮最有价值的产出）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | L4b 首判 0/3 | 侧栏「任务完成」计数被上一轮收尾触发，提交 2 秒就判分 | 改用界面 idle 窗口 |
| 2 | L5 首判 1/3 | 验收断言 `skipped/deleted` 计数，任务书只要求 `applied=0` | 严格按任务书改验收 |
| 3 | L6 首判 1/3 + 2 次报错 | ① 第二轮的「任务耗时」其实来自第一轮，秒判完成；② 「运行/跳过」授权框没识别；③ 编辑区滚出视口点不到 | 去掉耗时信号、按 DOM 找授权按钮、滚动进视口 |

三条规则现在是硬约束：

- 判分器自己要先被证伪：低分先看 trace 里有没有提前判分、验收有没有超出任务书；
- **每条隐藏验收必须能对到任务书的一句话**；
- **多轮任务不能复用单轮的完成信号**：上一轮的文本会留在页面里。

`tools/selftest.py` 守住第一、二类（23 个假 agent 用例），第三类只能靠真机跑出来。

## 下一步

1. **大仓库**：200+ 文件、同名函数、无关模块，考定位；这是唯一没试过的规模轴
2. **更多轮**：真实工作是 5+ 轮，L6 只有 2 轮；轮次越多，「会不会把上一轮改坏」越明显
3. **多工具对照**：同一任务换工具/模型跑，才轮得到「值不值得买」

## 边界

- 一个工具、一个模型、七个百行级任务；每任务 3 次只够说「稳定」，不够说「编程能力总分」
- `L4b` 的规则能在 README 和数据里对上；真实业务里的含糊比这更狠
- 判分只看行为，绕过验收（改 `conftest.py`、`sitecustomize.py`）靠 `forbidden` 拦，拦不全
- 耗时取 trace 与文件 mtime 的较大值，不含驱动器等待窗口；多轮任务含两轮之间的等待
- 驱动器会代点授权；真实使用中这一步是人工摩擦，授权次数已单独记录
