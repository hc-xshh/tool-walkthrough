# TRAE CN 3.4.4 编码能力判分（2026-10-22 / 10-23）

- 被测：TRAE CN 3.4.4，Agent 窗口，模型 `deepseek-v4-flash`，手动审批，本地执行
- 环境：Windows Server 2022，2560×1288，CDP 驱动；每轮一个独立 fixture 副本（git baseline + 快照）
- 方法：`code-eval/`，8 个任务 × 3 次 = **24 次尝试**（另有第一批 L1–L3 的 9 次，结论一致）
- 判分：隐藏验收（每个任务 8–11 条）始终在 agent 上下文之外，判分只看行为，不看 diff 长相

## 结论

**1. 八档任务都拦不住它。** 单文件、多文件、跨模块、六文件排错、只给症状、五条规则的长任务、
两轮需求变更、128 个文件的大仓库，全部 3/3。

**2. 规模没有增加成本，方向错了。** L7 用 128 个文件、7 成的噪声模块，结果比 L5 还快
（30–42 秒 vs 74–93 秒）——因为定位靠的是检索（`grep void`），不是逐文件阅读。真正让成本跳起来的
只有 L6 的多轮（238–272 秒），因为第二轮要重读上一轮的改动。**「文件多」不等于「难」，「要改的地方多、
要接着上一轮改」才是。**

**3. 成本是唯一稳定的区分信号。** 授权 2 → 3 → 4–7 次，耗时 17s → 85s → 255s，改动 +7 → +100。
L7 是个反例：改动最小（+1 行），所以再大的仓库也不贵。

**4. 剩下的轴：任务本身的设计质量。** 现在八个任务仍然是「一个明确的 bug + 一个明确的验收」。
还没试过：目标需要自己定义（「让这个报表更可信」）、多目标冲突、需要用户澄清才能继续。

## 判分器自己错了三次（这是本轮最有价值的产出）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | L4b 首判 0/3 | 侧栏「任务完成」计数被上一轮收尾触发，提交 2 秒就判分 | 改用界面 idle 窗口 |
| 2 | L5 首判 1/3 | 验收断言 `skipped/deleted` 计数，任务书只要求 `applied=0` | 严格按任务书改验收 |
| 3 | L6 首判 1/3 + 2 次报错 | ① 第二轮的「任务耗时」来自第一轮，秒判完成；② 「运行/跳过」授权框没识别；③ 编辑区滚出视口点不到 | 去掉耗时信号、按 DOM 找授权按钮、滚动进视口 |

三条规则现在是硬约束：

- 判分器自己要先被证伪：低分先看 trace 里有没有提前判分、验收有没有超出任务书；
- **每条隐藏验收必须能对到任务书的一句话**；
- **多轮任务不能复用单轮的完成信号**：上一轮的文本会留在页面里。

## 边界

- 一个工具、一个模型、八个任务；每任务 3 次只够说「稳定」，不够说「编程能力总分」
- `L4b` 的规则能在 README 和数据里对上；真实业务里的含糊比这更狠
- 判分只看行为，绕过验收（改 `conftest.py`、`sitecustomize.py`）靠 `forbidden` 拦，拦不全
- 耗时取 trace 与文件 mtime 的较大值，不含驱动器等待窗口；L6 含两轮之间的等待
- 驱动器会代点授权；真实使用中这一步是人工摩擦，授权次数已单独记录
- 办公任务只在参考产物上验证过判分器，没有真实 agent 数据
